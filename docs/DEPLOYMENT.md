# 다른 가게 운영자가 가입하는 공개 서비스 배포

현재 운영 주소는 https://haru-ocke.onrender.com/ 입니다. GitHub `main` 연결·Render 배포·Resend 발신 도메인 `mail.huphuphan.org` 인증을 진행했고, 사용자가 실제 앱 동작을 확인했습니다. 이 환경에서는 외부 접속 제한으로 운영 상태를 직접 조회하지 못했습니다. 아래 절차는 재배포·재구축을 위한 안내입니다. 개발 환경의 Publish와 웹사이트 배포는 별개입니다.

발신용 `huphuphan.org`의 DNS는 가비아에서 관리합니다. 기존 쇼핑몰에 연결된 `hup.kr`의 네임서버는 변경하지 않았습니다. 비밀 API 키는 Render 설정에만 보관하며 코드·문서에 적지 않습니다.

## 가장 먼저 할 일

1. [Render](https://dashboard.render.com/)에 GitHub 계정으로 가입하거나 로그인합니다.
2. 기존 도메인이 있는지 확인합니다. 앱 접속 주소는 Render가 제공하므로 처음부터 별도 웹 도메인을 살 필요는 없습니다.
3. 이메일 확인·비밀번호 재설정 메일을 보낼 발신 도메인이 필요합니다. 기존 도메인이 있으면 재사용할 수 있습니다. [Resend](https://resend.com/)에서 발신 도메인을 등록하고 표시되는 DNS 레코드를 도메인 관리 화면에 넣어 인증합니다. 발신 도메인은 앱 주소와 달라도 됩니다. Resend의 테스트용 기본 발신 주소는 불특정 다수 사용자 가입용으로 사용하지 않습니다.

계정 비밀번호·API 키는 채팅으로 보내지 않습니다. 사용자 본인이 각 서비스의 설정에 입력합니다. 유료 서버·디스크·도메인을 생성하기 전에 제공업체가 표시하는 비용을 확인합니다. 현재 가격을 이 문서에서 보장하지 않습니다.

## 코드 업로드와 Render 설정

1. 이 작업공간의 소스 코드를 선택한 GitHub 저장소에 커밋·푸시합니다. 초기 저장소에는 커밋이 없었으므로, 로컬 파일이 있다는 것만으로 Render가 코드를 읽을 수 있는 것은 아닙니다. `.env`, 실제 DB, 백업, `node_modules`는 업로드하지 않습니다. `.env.example`만 설정 예시입니다.
2. Render에서 GitHub를 연결하고 `lxxgoya/f-b_tools` 저장소 접근을 허용합니다. 비공개 저장소도 연결할 수 있으며 소스 코드를 공개할 필요는 없습니다.
3. Render의 Blueprint 배포에서 이 저장소의 `render.yaml`을 선택합니다.
4. 설정을 검토합니다. 파일에는 Singapore 리전, Starter 서버, 1GB 영구 디스크가 지정되어 있습니다. **무료 임시 디스크로 바꾸면 SQLite 데이터가 배포·재시작 과정에서 유실될 수 있습니다.** 다른 요금제를 선택하더라도 영구 디스크는 유지합니다. 단일 인스턴스로 실행합니다.
5. 비밀 설정 필드에 Resend에서 생성한 `RESEND_API_KEY`를 입력합니다. 발신 주소 `MAIL_FROM`에는 인증한 도메인의 이메일을 넣습니다. 예: `Haru <hello@실제도메인>`.
6. 서버 생성 전 화면에 표시된 비용을 확인한 뒤 배포를 진행합니다.
7. Render가 실제로 발급한 HTTPS 주소를 사용합니다. 주소를 미리 추정하지 않습니다.

Render는 `RENDER_EXTERNAL_URL`을 제공하며 서버는 이를 기본 공개 주소로 사용합니다. 사용자 도메인을 연결한 후에는 Render 설정에 `APP_ORIGIN=https://실제주소`를 지정하고 다시 배포합니다. URL 경로나 임의 값을 넣지 않습니다.

| 설정                                  | 역할                                               |
| ------------------------------------- | -------------------------------------------------- |
| `NODE_VERSION=24.19.0`                | 검증에 사용한 Node.js 버전                         |
| `DATABASE_PATH=/var/data/haru.sqlite` | 영구 디스크의 실제 DB                              |
| `TRUST_PROXY_HOPS=1`                  | Render 앞의 프록시를 거쳐 온 클라이언트 IP 처리    |
| `RESEND_API_KEY`                      | 메일 발송용 비밀값; 호스팅 설정에만 입력           |
| `MAIL_FROM`                           | Resend에서 인증한 도메인의 발신 주소               |
| `APP_ORIGIN`                          | 선택. Render 기본 주소 대신 사용할 실제 HTTPS 주소 |
| `BACKUP_DIRECTORY`                    | 선택. 기본값은 DB와 같은 디스크의 `backups/`       |

`TRUST_PROXY_HOPS`는 직접 연결 환경에서 0을 사용하고, 다른 프록시 구조로 옮길 때 실제 네트워크 경로에 맞춰야 합니다. 프록시가 전달한 클라이언트 IP를 검증 없이 무조건 신뢰하도록 변경하지 않습니다.

## 공개 전에 실제 주소에서 확인하기

- 본인 이메일로 가입하고 받은 확인 메일의 링크를 열어 가게를 등록합니다. 확인하지 않은 계정은 협업 데이터에 접근할 수 없어야 합니다.
- 로그아웃하고 비밀번호 재설정 메일을 받아 새 비밀번호로 로그인합니다. 이전 로그인 세션이 무효화되는지 확인합니다.
- 협업을 만들고 체크리스트, 문서/PDF, 정산·기록까지 확인합니다.
- 서버를 다시 시작해도 계정·가게·협업이 남는지 확인합니다.
- Render 로그에서 `Database backup verified`를 확인하고 백업 파일을 복원 테스트용 환경에서 열어봅니다.
- 다른 계정으로 로그인했을 때 첫 계정의 가게·협업이 보이지 않는지 확인합니다.

메일 공급자 연결과 실제 수신은 외부 계정·발신 도메인이 설정된 이후에만 검증할 수 있습니다. 로컬 자동화 테스트는 테스트용 메일 함수를 사용하며 실제 외부 수신자에게 메일을 보내지 않습니다.

## 백업과 복원

프로덕션 서버는 시작 시, 이후 12시간마다 SQLite backup API로 일관된 백업을 만들고 `integrity_check`를 확인합니다. 최근 14개를 유지합니다. 재시작도 백업을 만들기 때문에 보관 기간이 정확히 7일인 것은 아닙니다.

수동 백업은 서버 셸에서 `npm run backup`으로 실행합니다. 기본 경로는 `/var/data/backups`입니다. **같은 디스크의 백업은 디스크·계정 장애에 대한 외부 백업이 아닙니다.** 공개 서비스 운영자는 별도 보관 위치로 백업을 옮기고, 접근 권한·암호화·보존 기간과 복원 확인 일정을 정해야 합니다. 이 작업에서는 외부 저장소를 생성하거나 자격증명을 요청하지 않았습니다.

복원은 먼저 앱을 중지하고 현재 DB·WAL·SHM 파일을 복구 가능한 별도 위치에 보관한 뒤 수행합니다. 검증한 백업을 DB 경로에 복사하고, 이전 WAL/SHM이 새 DB에 재사용되지 않도록 원본과 함께 분리합니다. 파일 소유권을 서비스 사용자에 맞추고 재시작합니다. 운영 중 DB 파일만 덮어쓰거나 WAL을 임의로 삭제하지 않습니다. 먼저 테스트 환경에서 복원을 확인합니다.

## 서비스 운영자가 채워야 할 내용

서비스 운영자 이름·연락처, 개인정보 수집 항목·목적·보유 및 삭제 방침, 사용 중인 호스팅·메일 업체와 실제 데이터 처리 위치, 이용 조건·문의 창구를 정해야 합니다. 이 정보는 추정해서 개인정보처리방침으로 게시하지 않았습니다. 계정 삭제·데이터 내보내기, MFA, 직원 초대·공동 권한은 아직 제공하지 않으며 지원 절차 또는 추가 개발이 필요합니다. 문서 초안의 법률 검토도 별개입니다.

권장 배포는 Render의 네이티브 Node.js 런타임입니다. 컨테이너 빌드는 이 환경의 컨테이너 네트워크에서 의존성 설치가 끝나지 않아 검증하지 못했으며, Docker 배포 설정은 포함하지 않습니다.
